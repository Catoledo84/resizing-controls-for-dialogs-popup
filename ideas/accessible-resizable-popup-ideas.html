Accessible resizable popup — 3 design ideas

All three keep your current modal look (title bar + close ✕). The difference is how the resize control is exposed and how it works for keyboard + screen-reader users. Try tabbing to each handle and pressing arrow keys.

Idea 1 — Corner grip (WAI-ARIA splitter)

Familiar bottom-right diagonal grip, like OS windows. Made focusable and driven by arrow keys.

Focus the grip, then: ← ↑ → ↓ resize · Shift+arrow = big step · Home min · End max · Enter reset.

Idea 2 — Edge splitter bars

Separate right edge (width) and bottom edge (height) handles — the classic APG "window splitter". Clearer target, one axis each.

APG pattern Keyboard ✓ Screen reader ✓

Popup page

Drag the right bar to change width, the bottom bar to change height.

Tab to a bar: right bar ← → width · bottom bar ↑ ↓ height · Home/End min/max.

Idea 3 — Size buttons in the title bar

No dragging at all — explicit − / + buttons plus presets. The most discoverable and the easiest to get right for a11y. Great alongside Idea 1.

Most discoverable Keyboard ✓ Screen reader ✓

Popup page

Use the − and + buttons, or the maximize toggle, in the header.

Standard buttons — reachable by Tab, activated with Enter/Space. Pair with a corner grip for mouse users.

Idea 4 — Corner grip + floating key hint

Idea 1's grip, plus a small popover that appears only when the grip gets keyboard focus, listing exactly what the keys do. Fades out when focus leaves.

Discoverable Keyboard ✓ Screen reader ✓

Popup page

Tab to the corner grip → a keyboard guide pops up next to it.

Resize with the keyboard

  • ←→ width · ↑↓ height
  • Shift + arrow — bigger steps
  • Home smallest · End largest
  • Enter reset · Esc close popup

The hint is a non-focusable role="tooltip" tied to the grip via aria-describedby, so screen readers announce it too. It never traps focus.

Is a floating keyboard-hint menu a good a11y pattern?

Short answer: yes, when it's built as a description, not a widget. Showing instructions on focus is a recognized, encouraged technique (it satisfies the spirit of WCAG 3.3.5 Help). But there are right and wrong ways to build it.

DoAvoid
✓ Trigger it on focus (and hover), so keyboard users get it automatically. ✕ Only on hover — keyboard users never see it (WCAG 1.4.13).
✓ Make the hint non-focusable and tie it to the grip with aria-describedby so it's read aloud. ✕ Putting focusable items inside it — that adds tab stops and can trap keyboard users.
✓ Keep it dismissible and let Esc still close the popup. ✕ Auto-hiding on a timer, or covering the resize target itself.
✓ Respect prefers-reduced-motion for the fade/slide. ✕ Big animations, or showing it for every control (hint fatigue).
✓ Offer a "don't show again" once learned, or keep it very small. ✕ A large panel that obscures content each time focus lands.

Alternatives / complements to the popover: (1) a persistent tiny "⌨ shortcuts" link in the title bar opening the same list; (2) instructions in the grip's aria-label/aria-describedby only (no visible popover) — leanest, SR-only; (3) a one-time coach-mark on first use. The popover in Idea 4 is a good default because it's visible (helps sighted keyboard & low-vision users) and announced (helps SR users), without adding tab stops.

Recommended: compose an accessible modal (native <dialog> / Radix / Ariakit — focus trap + Esc + focus-return) with a hand-built Window Splitter handle: role="separator", tabindex="0", aria-controls, aria-label, aria-valuemin/now/max + aria-valuetext for spoken size, a visible focus ring, and arrow-key stepping (Shift/Page for coarse, Home/End for min/max). Keep Esc for closing the dialog. Idea 1 (corner grip) is the best default; add Idea 3 (size buttons) for maximum discoverability.
